# DOC-02, DOC-03 and DOC-04 · Persistent extension objects

Accepted with verification. The [document contract](../contracts/document.md) defines authoring and persistence. Runtime, benchmark and migration gates are pending.

## Decision

Embed one shared, versioned record at each app-owned attachment. A filter or adjustment augments a regular layer or object. Native extension variants supply new layer, procedural, geometry, scene and timed object roles. App equivalents keep ordinary placement and properties. Plugin records carry specialized data, asset references, typed property schemas and host-remappable links. Stable virtual children support editable overrides. Use one host record format in CL `plugin-api::doc`, the dependency-free SDK domain crate. (The workshop first named the beta-only `ext-core::project`, which is absent from current CL main; the final reconciliation moved it.) That keeps the common format in the same SDK identity owner. The record carries `Provenance(Chain)` and binds by `PackageId + TypeKey + SchemaVersion`, never by the host-local `LineageKey`. App serializers keep control of their formats.

A sidecar model behind stand-in objects would require synchronizing copy, undo and render against a second document structure. A loose EffectCraft asset directory would complicate Save As, recovery and collection. Use a single asset-bearing archive for portable EC documents, including complete recovery generations. Keep existing EC text for documents with no embedded extension assets. Keep PC's bounded manifest and blob layout. Put opaque bytes behind a stable host header with a forward read-only/refusal path. An older app either understands the entire file it opens for editing or refuses to overwrite it. Test actual old readers. PhotoCraft's exact pinned source independently confirms the version gate ahead of model conversion. Alternatives and evidence (review record kept outside this repository) · [PhotoCraft version gate](https://github.com/storytold/craft-libs/blob/bafb4522899d9f814a07dad636cdefcbf705dead/crates/pcraft-format/src/migrate.rs#L19-L35)

Retain every missing dependency's record and valid authored assets. Load and remap do not confer access or execute migrations. An authorized migration is one staged Undo. A render request carries purpose and dependency provenance. Exact export uses complete stages or a verified matching exact bake. An unverified bake can appear as an attributed preview or become authored output through an explicit flatten. Native editable save records appearance failures separately. Engine role negotiation distinguishes EC's native scene/timeline integration from PC's still/image-domain providers. A PhotoCraft plugin can compose a projected 3D view or rasterized 3D output through the shared authored-view and processor contracts. PhotoCraft does not advertise native scene/light, track or audio roles until real host providers exist.

## Review resolution

Q1 establishes native attachment and virtual-child ownership. Q2 uses an atomic identity, reference and asset transfer. Q3 uses a native writer version guard and byte-preserving migrations. Q4 uses scoped links and complete embedded closures. Q5 uses explicit render purpose and trusted exact coverage. Q6 uses typed app property and inspector providers. Q7 bounds temporal recursion and invalidation. B's six changes are accepted. C passed with amendments, including revision/durability receipts, refusal for opaque future headers, authority independent of digests, provenance that cannot be self-certified by imported files, full role/transfer checks and bounded parsing and recursion. Reconcile time recurrence and processor leases in the render rounds.

Measure paired 1,000-instance native open/save, state-byte copies during snapshots, reference remap work and autosave throughput versus streaming its captured closure to the same volume. Also measure 64 KiB state-hash preparation without repeated hashing on cache lookup. Target ≤5% open increment in the comparable known-byte fixture and zero copy of opaque state on snapshot clone. These are hypotheses. [Acceptance cases](../implementation/document-acceptance.md)

The Q, A1, B, A2 and C review roles ran in order. Q, B, C and lead used GPT-6.2 Sol high. Claude Opus 5.5 high delivered both architect replies after the initial Sol attempt reached its usage limit.
